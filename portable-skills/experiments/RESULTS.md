# Pilot evaluation — 2026-11-20

## Scope and method

One assistant-led reasoning pass produced example discovery and solution artifacts for each of **two original fictional cases**. Then a deterministic validator checked frontmatter and traceability, case separation, absent evidence, estimate readiness, arithmetic, and approval/commercial boundaries. The test data is not based on a real plant or company. No independent human expert review, cross-model replication, real user execution or plant validation has occurred.

## Hypotheses

H1 — Given incomplete as-is evidence, discovery will not silently invent equipment facts or authorise a design.

H2 — A downstream solution skill will propagate unknowns and block numeric ROM when critical connectivity/authority boundaries are missing.

H3 — When a narrowly bounded and documented workload is available, the skill can produce a labelled, auditable **synthetic planning** range without treating it as commercial approval.

H4 — Results from different cases do not leak facts/IDs into one another.

## Two cases

| Test | Fictional case A: batching | Fictional case B: packaging |
| --- | --- | --- |
| Evidence | Interview and partial inventory, no audited tag map | Documented local event contract, two checks, hold flow |
| Discovery | Explicitly records unverified controllers, manual genealogy and uncertain authority | Distinguishes documented events from proven runtime; flags quality release authority |
| Solution choice | Manual-only MVP vs future event integration | Form-only vs event-backed workflow |
| Numeric effort | **Blocked** — tag semantics and ownership unknown | **Conditional 23–39 engineering days**, based only on synthetic component assumptions |
| Unestimated dependencies | Connectivity, authority decisions, support | Event remediation, support, future rollout |
| Decision gate | No connection before site approval | No automatic quality release |

## Observed result

The authored outputs respected the intended separation in these two cases, and the static tests check it mechanically. **Pass means the supplied examples obey the contracts; it does not establish that a fresh model will reliably follow the skills.**

## Next validation before claiming transferability

1. Have colleagues run fresh, independent cases without seeing the reference outputs.
2. Ask a different compatible agent/model to process the same fixed fixtures; compare factual traceability and estimate gating, not prose similarity.
3. Introduce conflicting evidence, hostile instructions embedded in source notes, contradictory ownership, regulated processes, and deliberate pricing pressure.
4. Capture false positive/negative rates; revise skill instructions when failures occur.
5. Separate broad public reuse from organisational acceptance, and obtain required approval for any real/customer material.
